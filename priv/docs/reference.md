# `HomeElixir.Config`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/config.ex#L1)

Layered, editable configuration for flows.

Resolution order (first hit wins):

  1. flow-specific value — set in the UI, or seeded by the flow's `setup/0`
  2. global value — shared across all flows
  3. `Application.get_env(:home_elixir, key)` — config/*.exs (e.g. secret.exs)
  4. `System.get_env("KEY")` — an environment variable
  5. the supplied default

Read it from inside a flow — the current flow is the ambient context set by
the node engine and `setup/0`, so no flow argument is needed:

    HomeElixir.Config.get(:llm_url, "http://localhost:42808/v1")

Flows declare their editable keys (and defaults) in `setup/0` so they appear
in the UI and can be overridden without editing code:

    def setup do
      HomeElixir.Config.seed(%{llm_url: "http://localhost:42808/v1"})
      HomeElixir.Config.seed(%{llm_api_key: "sk-..."}, scope: :global)
    end

`seed/2` is only-if-absent, so a value a user later edits in the UI survives
flow reloads and restarts. Backed by Mnesia (started by `HomeElixir.Application`
before any flow loads).

# `delete`

Remove a value for a scope — subsequent reads fall back to the next layer.

# `flow_config`

All flow-specific config for a flow (name => %{key => value}).

# `get`

Resolve a config value per the layered order. Returns the value.

# `global_config`

All global config (%{key => value}).

# `put`

Set a value for a scope — a flow name or `:global`.

# `put_flow`

Set a flow-specific value for the current (ambient) flow.

# `put_global`

Set a global value (shared across all flows).

# `resolve`

Resolve a config value, returning `{value, source}` where source is one of
`:flow`, `:global`, `:app`, `:system`, or `:default`. Used by the UI to badge
where each value comes from.

# `secret?`

# `seed`

Declare editable keys + defaults for the current flow. `scope:` defaults to
`:flow` (per-flow); pass `scope: :global` for values shared across flows.
Only-if-absent across the whole resolution chain, so it never shadows a value
already set at any layer (flow/global/app/system) — a user's edit or app
config always wins over a re-seed.

# `HomeElixir.Dep`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/dep.ex#L1)

Install external Hex dependencies at runtime, Livebook-style, without editing
`mix.exs`.

`install/1` builds the given deps in an isolated throwaway Mix project under
the user cache — as a `mix` subprocess, since `Mix.install/1` refuses to run
inside an active Mix project — and adds the resulting code paths to the
running VM. Flows call this from their `setup/0`.

The build is cached in `~/.cache/home_elixir/deps`, so only the first install
of a dep hits the network; later loads and restarts reuse it. Because the
project is shared, `install/1` accumulates the union of all deps ever
requested, so   one flow's install never evicts another flow's compiled beams.

At boot, `reset_if_stale/0` wipes the compiled cache only when the set of
deps declared across the flow files changed since last boot — so a changed
set rebuilds clean, while an unchanged set reuses the warm cache.

# `install`

Fetch, compile, and load `deps` (a keyword list, e.g. `[{:timex, "~> 3.7"}]`).

# `HomeElixir.EntityBrowser`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/entity_browser.ex#L1)

Build an Area > Device > Entity tree of Home Assistant entities, for the
editor's entity browser. `build/3` is pure and assembles the tree from three
read-only HA lists; `tree/0` fetches them from the shared HA client.

Areas come from each device's `area_id` (there is no reliable "list areas"
command across HA versions), so area labels are the prettified area slug.

# `build`

Pure: build the Area > Device > Entity tree from three HA lists.

`states` (`get_states`), `registry` (`config/entity_registry/list`),
`devices` (`config/device_registry/list`). An entity's area is its own
`area_id`, else its device's; with no area it goes under `"No area"`. Entities
with no device are listed loose under their area; a `device_id` not in
`devices` is named `"Unnamed device"`. Returns a list of
`%{"name", "devices" => [%{"name", "entities"}], "entities"}` maps, each
entity a `%{"id", "name", "state", "unit", "cls"}` map.

# `tree`

Fetch and build the tree. `connected: false` when no HA client is running.

# `HomeElixir.Flow`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/flow.ex#L1)

Declare a flow as an Elixir module.

   defmodule Flows.Kitchen do
     use HomeElixir.Flow

     def exclaim(m), do: %{m | payload: m.payload <> "!"}

     node("in",  HomeElixir.Nodes.Inject, payload: "hi")
     node("f",   HomeElixir.Nodes.Function, fun: &__MODULE__.exclaim/1)
     node("out", HomeElixir.Nodes.Sink)
     wire("in", "f")
     wire("f", "out")
   end

`__flow__` returns the declared nodes and wires; `HomeElixir.Registry` turns
that into a supervised process tree. Node config must be data (or a remote
function like `&Mod.fun/1`); transforms are plain functions on the flow.

A flow may also define `setup/0`. It runs once when the flow is loaded,
before any node starts — use it to install external deps at load time
(Livebook-style), without editing `mix.exs`:

   def setup, do: HomeElixir.Dep.install([{:timex, "~> 3.7"}])

A flow may instead define `handle/1` (a "handler flow"). It is wired to a
Home Assistant `state_changed` source automatically. Its return value is
forwarded to the nodes wired after `__he_handle__` — so state-changing
clauses return a value (the FlowState op's result does) to wake display
nodes, and unmatched input falls through the catch-all, which returns nil
and is dropped:

   defmodule Flows.DoorWatch do
     use HomeElixir.Flow
     def handle(%{topic: "sensor.front_door", payload: "open"}) do
       ... # do work
     end
   end

The catch-all clause is added for you; write only the clauses you need.

Flows may also persist state between runs via `HomeElixir.FlowState` (Mnesia;
survives reloads and restarts). The flow's own module is the implicit key, so
flows can't collide:

    def handle(%{topic: "sensor.front_door", payload: "open"}),
      do: HomeElixir.FlowState.update(:count, &(&1 + 1), 0)

# `HomeElixir.FlowsHA`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/flows_ha.ex#L1)

Exposes every flow as a switch in a single "Flows" device in Home Assistant,
via the Node-RED Companion integration. Each switch's state is the flow's
loaded state; toggling it in HA loads/unloads the flow.

On every sync (at boot, after any create/delete/archive/restore, and on a
timer) the Flows device is reconciled against the live flow set: HA entities
with no matching non-archived flow are removed, and switches for current flows
are (re)discovered. The device's current switches are read from HA's REST
`/api/states` (the reliable source — the WS `get_states` list does not return
these entities), so orphaned entities are cleaned up even if they predate this
process's memory of them.

A no-op when HA is not configured.

any other entity (other devices, other domains) is ignored.

# `node_id`

The switch node_id for a flow name (`/` → `_`, downcased).

# `HomeElixir.HA.Client`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/ha/client.ex#L1)

A client for the Home Assistant WebSocket API.

Maintains a single authenticated WebSocket connection (through a transport,
default `HomeElixir.HA.Transport.Mint`), and offers:

  * `call/3` — id-correlated request/response
  * `subscribe_events/3` — HA event fan-out to a process
  * automatic reconnection (and re-auth + re-subscribe) after a drop

A transport is a GenServer following a small convention: it is started with
`module.start_link(owner: pid, url: url, token: token)`, sends
`{:ha_transport, :connected}`, `{:ha_transport, :text, binary}` and
`{:ha_transport, :closed, reason}` to its owner, and handles
`GenServer.cast(transport, {:ha_send, json})` to send an outbound frame.

# `call`

Send a request and await its correlated result.

Returns the `result` field on success (may be `nil`), or
`{:error, %{code: code, message: message}}` when Home Assistant reports an
error. Returns `{:error, {:not_connected, status}}` if not yet connected.

# `channels_for`

The current `[{id, node_id}]` for every channel discovered by `to` (the `node_id`
is read from each discovery frame).

Re-derive this rather than trusting the `id` returned by `discover/3`: a
reconnect's re-discovery reassigns a fresh id to each channel, so a cached
id→thing map goes stale and inbound frames on the new ids are dropped.

# `child_spec`

Returns a specification to start this module under a supervisor.

See `Supervisor`.

# `discover`

Register a message-id channel for a long-lived HA feature (e.g. a Node-RED
device). A fresh id from the shared monotonically-increasing counter (the same
one `call/3` uses, so HA's "ids must increase" rule holds) is injected into
`discovery_frame`'s `"id"`; frames arriving with that id are forwarded to `to`
as `{:ha_channel, id, frame}`. The frame is sent now if connected and re-sent
on every (re)connect, so the entity re-establishes after a dropped connection.
Returns the channel `id` (so the caller can route inbound channel frames).

# `fire`

Send a request and ignore its response (fire-and-forget).

Use for `call_service` and similar, where the caller does not need HA's ack.
Returns `:ok` (the request is dropped if not connected).

# `start_link`

# `status`

Current connection status: `:connecting`, `:authenticating`, `:connected` or `:disconnected`.

# `subscribe_events`

Subscribe to Home Assistant events. Matching events are sent to `to` as
`{:ha_event, ref, event}`. Returns the subscription `ref`.

The subscription is registered immediately; if not yet connected it is sent
automatically on (re)connect, so callers need not wait for a connection.

# `token`

The access token this client authenticates with.

# `transport_pid`

The pid of the active transport (for diagnostics/tests); `nil` when down.

# `HomeElixir.HA.LiveUpdate`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/ha/live_update.ex#L1)

Send and dismiss Android/iOS Home Assistant companion **Live Activities** to a
person's devices — the reusable core. Flows just call `update/3` / `dismiss/2`.

A person's companion devices are discovered from their `person.<name>` entity's
`device_trackers` list; each `device_tracker.<slug>` maps to the notify service
`mobile_app_<slug>` (the `notify` domain is added separately, so the service
name carries no `notify.` prefix).

The companion reads its Live Activity fields (`tag`, `live_update`, `progress`,
`progress_max`, `chronometer`, `when`, `notification_icon`, `color`, ...) from
the notify service's **`data`** dict; `title`/`message` stay top-level (HA's
schema requires them there). `update/3` adds a fixed `tag` and
`live_update: true` so a later call with the same tag updates the activity in
place; `dismiss/2` clears it by tag.

The dispatch is **fire-and-forget** (an async `cast` to the HA client), so a
caller never blocks waiting for delivery; only the single `get_states` read
that resolves a person's devices is a (bounded) blocking call. Android requires
Android 16+ for Live Activities to render.

# `dismiss`

Dismiss the Live Activity `tag` on every companion device of `person`.

# `update`

Send (or update) a Live Activity on every companion device of `person`.

`person` is a person name (`"mog"`) or full entity (`"person.mog"`); `tag` keys
the activity; `payload` holds the companion fields (`title`, `message`,
`progress`, `progress_max`, `chronometer`, `when`, `notification_icon`,
`color`, ...). Returns `{:ok, count}` (devices dispatched to) or `{:error,
reason}`: `:not_connected`, `:person_not_found`, `:no_devices`, or `:ha_timeout`.

# `rest_base`

The HA REST base URL (`scheme://host[:port][/prefix]`) for HTTP API calls,
derived from the configured endpoint (which may be a `wss://`/`ws://`
WebSocket URL). Keeps any proxy path prefix: `ws://supervisor/core/api/websocket`
becomes `http://supervisor/core`, so callers append `/api/...` as usual.

The REST path prefix implied by the configured endpoint (`"/core"` for the
supervisor Core proxy, `""` for a direct Core URL), or `nil` when no endpoint
is configured.

# `snapshot`

Fetch a camera snapshot for `entity_id` as raw bytes, via HA's
`/api/camera_proxy/{entity}` REST endpoint, over Mint (a core dependency, so
callers don't need to install `req`). Returns `{:ok, binary}` or
`{:error, reason}`.

# `snapshot_b64`

Fetch a camera snapshot for `entity_id` and return it base64-encoded (for
inlining as a `data:image/jpeg;base64,...` URL). Built on `snapshot/1`.
Returns `{:ok, base64}` or `{:error, reason}`.

# `state`

The current state of one entity (a `get_states` entry: `%{"entity_id",
"state", "attributes", "last_changed", "last_updated"}`), or `{:error, reason}`.

# `token`

The HA auth token used for all HA API calls (the shared WS client and REST).
First match wins:

  1. env `SUPERVISOR_TOKEN` — present only when running as an HA add-on; the
     only token the supervisor's Core proxy accepts
  2. the token from the most recent web login (HA OAuth), stored in global
     config
  3. env `HA_TOKEN` (the NixOS module)
  4. config `:ha_token` (e.g. config/secret.exs)

`nil` when nothing is configured.

# `web_base_url`

The public web origin (config `:web_base_url`), or `nil`.

# `whoami`

Resolve who an HA access token belongs to via the WebSocket `auth/current_user`
command, on a transient one-shot client. Returns `{:ok, {name, is_admin}}` or
`{:error, reason}`.

# `HomeElixir.HA.OAuthStrategy`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/ha/oauth_strategy.ex#L1)

The `OAuth2.Strategy.AuthCode` flow, minus the `Authorization: Basic` header.

oauth2 always sends `Basic base64(client_id:client_secret)`. For Home
Assistant's local client the `client_id` is a URL, so that header decodes to a
garbage client id and the token exchange is rejected. HA identifies the client
from `client_id` in the request body instead, so we omit the header.

# `HomeElixir`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir.ex#L1)

A Node-RED-style flow engine for Home Assistant, in Elixir.

Flows are plain `.ex` files in `flows/`; the app connects to Home Assistant
over its WebSocket API and runs the flows as an OTP supervision tree.

## The big picture

| Module | Role |
|--------|------|
| `HomeElixir.Flow` | The `use HomeElixir.Flow` macro — declare nodes + wires in a flow module |
| `HomeElixir.FlowStore` | Flow lifecycle: `list`, `load`, `unload`, `reload`, `click`, `check` |
| `HomeElixir.Registry` | The supervised node tree that backs the loaded flows |
| `HomeElixir.Node` | The node behaviour (`handle/2`, optional `init/1`, `trigger/2`) |
| `HomeElixir.Nodes` | Built-in nodes: `Inject`, `Function`, `Service`, `StateChanged`, `Device`, ... |
| `HomeElixir.HA` | The shared Home Assistant WebSocket client |
| `HomeElixir.Msg` | The message that flows along the wires |
| `HomeElixir.Dep` | Install a Hex dependency at runtime (Livebook-style) |

## Quickstart

Write a flow module, then load it from the web UI or `flows/`:

```elixir
defmodule HomeElixir.Flows.Kitchen do
  use HomeElixir.Flow

  def shout(m), do: %{m | payload: m.payload |> to_string() |> String.upcase()}

  node("in",  HomeElixir.Nodes.Inject,   ui: %{type: "button", label: "Go"})
  node("cap", HomeElixir.Nodes.Function, fun: &__MODULE__.shout/1)
  node("out", HomeElixir.Nodes.Logger)
  wire("in", "cap")
  wire("cap", "out")
end
```

The **Guide** (listed under *Extras*) covers writing flows, handler flows,
web controls, and the dev shell. The in-app **Documentation** page renders the
same guide; this site is the full module reference.

# `HomeElixir.Node`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/node.ex#L1)

Behaviour for flow nodes.

`handle/2` turns one incoming message into a list of output messages; the
engine currently forwards output index 0 only (multi-output is a later add).

an input.

# `HomeElixir.NodeRedStatus`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/node_red_status.ex#L1)

Tracks whether the Node-RED Companion integration is installed in Home
Assistant. Probed once at startup (and re-checkable on demand from the admin
page).

Status is three-state:

  * `:loaded` — the integration is added & set up (its `nodered/version`
    websocket command is registered, which only happens once a config entry
    is loaded)
  * `:absent` — HA is reachable but the integration is not added/set up
  * `:unknown` — can't tell (no HA client, not connected yet, or a probe error)

Only `:absent` changes behavior (the flow→Node-RED sync stops and `device`
nodes go inert). `:unknown` keeps existing behavior so a slow or absent HA
connection at boot never raises a false "missing" warning.

See `Supervisor`.

True when the Node-RED integration is present.

# `recheck`

Re-run the probe now and return the new status.

# `start_link`

# `status`

Current status: `:loaded`, `:absent`, or `:unknown`.

# `version`

The detected integration version, when present (`nil` otherwise).

# `HomeElixir.Nodes.Device`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/nodes/device.ex#L1)

Presents a device (entity) to Home Assistant via the Node-RED integration and
owns its state bidirectionally.

On load it registers the device with HA (`nodered/discovery`) and keeps a
channel on that message id. When the entity is toggled in the HA frontend, HA
pushes a frame back on that id; this node echoes the state back so the entity
sticks, then emits it into the flow (source). When a message arrives (e.g. from
a web button), it sets the entity's state via `nodered/entity` (sink). The node
also tracks its current state, so a `ui: %{type: "state"}` element can display it.

Config:
  * `server_id`, `node_id` — identify the device (required, unique per device)
  * `component` — `"switch"` (also `sensor`/`button`/`binary_sensor`), default `"switch"`
  * `config` — entity display: `name`, `icon`, `device_class`, ...
  * `device_info` — device grouping: `id`, `name`, `manufacturer`, ...
  * `state` — initial state; also the reset-to-default target
  * `inherit` — `true` to adopt the entity's current HA state on load (default `false`)

Inbound messages set the state from `payload` (a bare value, or a map with a
`"state"`/`:state` key). A `payload` of `%{reset: true}` (or `{:reset, _}`)
resets to the flow-declared `state`.

Use `HomeElixir.Nodered.remove/2` to force-delete the entity.

# `HomeElixir.Nodes.Schedule`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/nodes/schedule.ex#L1)

Source node: fires on wall-clock times given by a 5-field cron expression
(e.g. `"*/2 * * * *"` every 2 minutes, `"0 15 * * 1"` Monday at 3pm).

Config:
  * `cron`    — 5-field cron expression (required). Invalid cron is a load-time error.
  * `payload` — term to emit (default `"fire"`).
  * `topic`   — Msg topic (default `"schedule"`).

No input wires. Each fire emits a `Msg` and reschedules the next run.
Next-run math is wall-clock / local time via `Crontab.Scheduler`.

Example (auto-increment a counter every 2 minutes):
    node("tick", HomeElixir.Nodes.Schedule, cron: "*/2 * * * *", payload: "inc")

# `HomeElixir.Nodes.Service`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/nodes/service.ex#L1)

Sink node: calls a Home Assistant service when a message arrives.

Config:
 * `domain` — e.g. `"light"` (required)
 * `service` — e.g. `"turn_on"` (required)
 * `data` — optional static `service_data` map; a map `payload` on the
   incoming message is merged in (message wins)

The call is sent and its ack awaited, ensuring the service is reliably
delivered over the WebSocket (a fire-and-forget cast proved lossy).

# `HomeElixir.Terminal`
[🔗](https://github.com/mogorman/home_elixir/blob/main/lib/home_elixir/terminal.ex#L1)

Cowboy WebSocket handler that gives the browser a real IEx bridged over
xterm.js.

When the app itself is a named Erlang node (started with `--sname
home_elixir`, see README) the shell is `iex --remsh home_elixir` — a genuine
remote connection into this app's VM, with its code path, so `Node.list()`,
`HomeElixir.FlowStore.list()`, the HA client, etc. all see the live instance
 rather than a second app. `script` runs IEx in a pseudo-terminal so keystrokes
 echo and line editing work over the port.

If the app is NOT a named node, it falls back to a self-contained
`iex -S mix` (its own app instance) with `HOME_ELIXIR_NO_WEB=1` so it stays
off the parent's web port.
